  <name>Task 1: FOUC fix — blocking script + ThemeProvider DOM init</name>
  <files>frontend/app/layout.tsx, frontend/components/ThemeProvider.tsx</files>
  <action>
Read node_modules/next/dist/docs/ before writing any Next.js code (per frontend/AGENTS.md).

In `frontend/app/layout.tsx`, add a `<script>` tag inside `<head>` using `dangerouslySetInnerHTML` with a blocking inline script that runs synchronously before React hydrates. The script should:
```js
(function(){
  try {
    var t = localStorage.getItem('theme');
    if (t === 'light') { document.documentElement.classList.remove('dark'); }
    else { document.documentElement.classList.add('dark'); }
  } catch(e) {}
})()
```
Add `<head>` as a sibling to `<body>` inside `<html>`. The layout currently has no explicit `<head>` — add one containing only this script. Do NOT use Next.js `<Script strategy="beforeInteractive">` — that requires client component and adds overhead; `dangerouslySetInnerHTML` on a plain `<script>` tag in the Server Component layout is correct for this use case.

In `frontend/components/ThemeProvider.tsx`, change the `useState` initialization from the hardcoded `"dark"` to read the current DOM state:
- Replace `useState<Theme>("dark")` with:
  ```ts
  const [theme, setTheme] = useState<Theme>(() => {
    if (typeof window === 'undefined') return 'dark';
    return document.documentElement.classList.contains('dark') ? 'dark' : 'light';
  });
  ```
- Remove the first `useEffect` that reads localStorage (it is now handled by the blocking script and the useState initializer).
- Keep the second `useEffect` that writes `localStorage` and updates `document.documentElement.classList` on theme changes.
- Keep the `toggle` function and context provider unchanged.

The result: the blocking script sets the correct class synchronously, ThemeProvider reads that class on mount (no flash), and subsequent toggles update both DOM and localStorage.

  <action>
The current page only checks `if (!user) redirect('/login')`. Add a role check after the user check.

Per the project decision logged in STATE.md: "Role sourced from app_metadata.role in JWT (set by Supabase admin)". The Supabase `getUser()` response includes `user.app_metadata` on the user object.

Update `frontend/app/app/admin/page.tsx`:
```ts
import { redirect } from 'next/navigation'
import { createServerSupabaseClient } from '@/lib/supabase/server'
import { SuggestionQueue } from '@/components/admin/SuggestionQueue'

export default async function AdminPage() {
  const supabase = await createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()

  if (!user) {
    redirect('/login')
  }

  const role = user.app_metadata?.role
  if (role !== 'admin') {
    redirect('/app/dashboard')
  }

  return (
    <main className="container mx-auto py-8 space-y-6">
      <h1 className="text-2xl font-semibold mb-6">Painel do Administrador</h1>
      <SuggestionQueue />
    </main>
  )
}
```

No additional imports needed — `user.app_metadata` is part of the Supabase `User` type already returned by `getUser()`. The redirect to `/app/dashboard` happens server-side before any data fetching or component rendering.
